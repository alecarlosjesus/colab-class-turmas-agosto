Regra de segurança

Execute uma ação por vez. Antes de trocar de branch, receber alterações ou integrar trabalho, consulte git status.

Pare se houver mudanças inesperadas: não use git restore, git reset, git clean ou exclusões forçadas apenas para fazer uma mensagem desaparecer. Primeiro descubra o que o Git está informando.

Privacidade: nunca publique senha, token, chave, arquivo .env ou link do Figma com permissão pública de edição.

Na primeira etapa do projeto, as mudanças foram registradas diretamente na main para simplificar o contato inicial com Git. A partir de agora, cada alteração relevante será feita em um branch próprio.

O que é um branch?

Um branch é uma referência móvel para uma linha de commits. Ele permite trabalhar em uma mudança sem alterar imediatamente a versão integrada do projeto.

Um branch não é uma cópia completa e independente de todos os arquivos. Internamente, ele aponta para commits e acompanha a evolução daquela linha de trabalho.

Por que usar branches?

Isolamento: uma mudança incompleta permanece no branch de trabalho e não altera a main.

Rastreabilidade: o nome do branch e seus commits explicam qual tarefa está sendo desenvolvida.

Revisão: o branch pode ser publicado e comparado antes de ser integrado.

Branch não substitui commit

Elemento

Papel

Branch

Organiza uma linha de trabalho.

Commit

Registra um estado do projeto nessa linha.

Merge

Integra mudanças de um branch ao branch atual.

Pull Request

Propõe, no GitHub, a revisão e a integração entre branches.

Sem commits, o branch não possui novos marcos para compartilhar. Sem branch, os commits podem ser feitos diretamente na main, mas o trabalho deixa de ficar isolado.

Enxergar a separação no histórico

Execute:

git log --graph --oneline --decorate --all -8

Como ler as opções

  • log: consulta o histórico;
  • --graph: desenha linhas que representam os caminhos dos commits;
  • --oneline: mostra cada commit em uma linha compacta;
  • --decorate: exibe referências como HEAD, main e origin/main;
  • --all: inclui todos os branches conhecidos;
  • -8: limita a saída aos oito commits mais recentes.

O resultado deve indicar:

Resultado

Quando ocorre

Efeito no histórico

Fast-forward

Fast-forward em linguagem simples

Se a main ficou parada e apenas o branch de trabalho recebeu commits, o Git pode simplesmente mover o ponteiro da main para a frente.

Merge de três vias em linguagem simples

Se a main e o branch receberam commits diferentes, o Git procura o ponto comum de origem e tenta combinar os dois caminhos.

Por que ocorre conflito?

O conflito não significa que o Git quebrou. Significa que duas mudanças não podem ser combinadas automaticamente sem que uma pessoa decida o conteúdo final.

O branch real do Conecta Campus será integrado pelo Pull Request. O próximo laboratório será separado e descartável para não colocar o projeto em risco.

Saída de emergência

Se você quiser cancelar um merge antes de criar o commit de resolução:

git merge --abort

Esse comando tenta retornar ao estado anterior ao início do merge.

Não use git merge --abort depois de concluir a resolução em um commit.

O que é um Pull Request?

Um Pull Request, também chamado de PR, é uma proposta de integração entre branches no GitHub. Ele não é apenas uma cópia e não é o mesmo que git pull.

A página do PR reúne:

  • descrição da proposta;
  • commits;
  • arquivos modificados;
  • comparação entre versões;
  • comentários;
  • revisões;
  • verificações automáticas, quando configuradas;
  • condições para o merge.

Revisão final do Pull Request

Antes do merge, confira:

  • [ ] base é main.
  • [ ] compare é feature/wireframe-inicial.

Fazer o merge no GitHub

  1. Confirme que a revisão foi concluída.
  2. Clique em Merge pull request ou use o método definido pelo repositório.
  3. Leia a mensagem de merge.
  4. Confirme a integração.
  5. Clique em Delete branch para remover o branch remoto integrado.
  6. Abra a main no GitHub.
  7. Confirme que docs/wireframe.md agora está na main.

O merge no GitHub não atualiza automaticamente seu computador. Sua main local ainda precisa receber o resultado.

Atualizar a main local

Volte ao terminal dentro de conecta-campus e execute um comando por vez:

git switch main
git pull
git branch -d feature/wireframe-inicial
git fetch --prune
git log --graph --oneline --decorate --all -10
git status

Entendendo cada comando

git switch main

Troca do branch de trabalho para o branch principal.

git pull

Recebe o merge realizado no GitHub e atualiza a main local.

git branch -d feature/wireframe-inicial

  • branch: gerencia branches;
  • -d: exclui com verificação de integração;
  • remove apenas o branch local;
  • não apaga a main nem o histórico integrado.

Se -d recusar, não troque automaticamente para -D. Primeiro confirme se o PR foi realmente mesclado e se git pull atualizou a main.

git fetch –prune

  • fetch: atualiza informações conhecidas sobre o remoto;
  • --prune: remove referências locais de branches remotos que já não existem;
  • não apaga seus arquivos de trabalho.

git log

Mostra o histórico e as referências após a integração.

git status

Deve indicar main e árvore de trabalho limpa.

Gabarito WP01

Branch é uma referência leve para uma linha de commits; ele não duplica todos os arquivos. Commit registra um estado. Branch organiza a sequência de commits. Pull Request propõe, no GitHub, a revisão e integração das mudanças.

Gabarito WP02

O branch atual e o branch do commit devem ser feature/wireframe-inicial. A main não contém wireframe.md apenas porque o arquivo existe no outro branch; ela o receberá após a integração.

Gabarito WP03

HEAD aponta para feature/wireframe-inicial. main e origin/main permanecem no commit anterior. Após o push, origin/feature/wireframe-inicial aponta para o commit enviado.

Gabarito WP04

HEAD identifica a versão do branch atual; ======= separa as versões; o nome final identifica o branch recebido. O caminho seguro é consultar git status, editar e remover os marcadores, executar git add e criar o commit que conclui o merge.

Gabarito WP05

base deve ser main; compare deve ser feature/wireframe-inicial. Em Files changed, verifique escopo, conteúdo real das linhas, ausência de segredos e coerência com a descrição.

Gabarito WP06

  1. Página.
  2. Frame.
  3. Camada de texto.
  4. Grupo.

Frame representa melhor uma tela porque possui dimensões e funciona como contêiner de camadas com propriedades próprias.

Gabarito WP07

O arquivo deve apresentar Texto/Titulo, Texto/Corpo, Cor/Texto, Cor/Superficie e Cor/Borda aplicados. O link precisa abrir em janela privativa e permitir visualização sem edição pública.

Gabarito WP08

A main foi atualizada e originou feature/wireframe-inicial. O documento foi registrado em commit; o branch foi publicado e usado em um Pull Request. No Figma, foram criados três wireframes, estilos e um link de visualização. O link gerou outro commit no mesmo branch. Depois da revisão, o PR foi mesclado, a main local recebeu git pull e os branches temporários foram encerrados.

Gabarito WP09

Exemplo: para CONFLICT, confirme com git status, resolva o conteúdo, use git add e conclua com commit. Evite apagar o arquivo inteiro ou forçar uma troca de branch.

Outro exemplo: se o link do Figma pede acesso, teste em janela privativa e ajuste a permissão para visualização. Evite liberar edição pública.

Gabarito WP10-A

  1. git switch -c feature/exemplo - terminal.
  2. Criar commit - terminal.

Gabarito WP10-B

A alteração pode ser parte de um trabalho real ou ter sido feita por engano. Se estiver pronta e coerente, revise e crie um commit antes de trocar. Se estiver incompleta, permaneça no branch e procure uma forma consciente de concluí-la ou guardá-la. Não use descarte forçado sem entender o conteúdo.
